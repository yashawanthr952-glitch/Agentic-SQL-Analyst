# Agentic SQL Analyst

A text-to-SQL agent built with LangGraph: **plan → generate → validate → execute → repair**
against PostgreSQL, served by FastAPI, with a React frontend that shows the whole
graph trace. The read-only guardrail parses generated SQL into an AST and is
tested against an adversarial fixture set.

---

## The loop

![Agent graph flow](docs/flow-of-the-loop.png)

<details>
<summary>Text version of the diagram</summary>

​```
START ─→ plan ─→ generate ─→ validate ──ok──→ execute ──ok──→ END (succeeded)
...
​```
</details>

Five real nodes, not one prompt. Each is a pure `state -> partial state`
function in [agent/nodes.py](agent/nodes.py); the wiring is in
[agent/graph.py](agent/graph.py).

| Node | Does | Reads | Writes |
| --- | --- | --- | --- |
| `plan` | Decomposes the question into steps and tables. No SQL. | `user_query` | `plan`, `plan_tables` |
| `generate` | The only node that emits SQL. | `plan`, `repair_instruction` | `generated_sql` |
| `validate` | AST guardrail; fails closed. | `generated_sql` | `validation_result`, `safe_sql` |
| `execute` | Runs `safe_sql` read-only with a server-side timeout. | `safe_sql` | `execution_result` or `db_error` |
| `repair` | Classifies the failure, builds the retry instruction. No model call. | `db_error` or `validation_result` | `repair_instruction`, `retry_count` |

## Why each guardrail exists

### Why an AST and not a regex

A regex denylist operates on *characters*. Postgres operates on a *parse tree*.
Every place those two models diverge is an exploit, and the divergences are not
enumerable:

| Input | Why a regex loses |
| --- | --- |
| `DELETE/**/FROM t` | comments are token separators |
| `SELECT 'DROP TABLE x'` | keyword inside a string literal — false positive |
| `$tag$ DROP TABLE x $tag$` | dollar quoting, arbitrary delimiter |
| `WITH d AS (DELETE FROM t RETURNING *) SELECT * FROM d` | the write is nested; the statement reads as a SELECT |
| `SELECT * INTO exfil FROM users` | creates a table containing no forbidden keyword at all |

You cannot finish that list — that is the point. A denylist is unbounded because
it enumerates badness; an allowlist over a grammar is finite because it asserts
the shape of what you accept. Parsing converts "is this string dangerous?" into
"is every node in this tree permitted?", which is a question with an end.

The honest caveat: `sqlglot` is not the Postgres parser. It approximates the
grammar and the two will occasionally disagree. That is exactly why the
validator **fails closed** — a disagreement then surfaces as a rejected valid
query (annoying, and the repair loop recovers from it) instead of an accepted
dangerous one (fatal). Failing closed is a decision about which direction the
errors point, not a coding style.

### Why the tree walk, not just the root node

Two statements decide whether the guardrail is real:

```sql
WITH d AS (DELETE FROM orders RETURNING *) SELECT * FROM d
SELECT * INTO exfil FROM customers
```

Both are valid Postgres, both **root as a `Select` node**, and one of them
contains no forbidden keyword. A validator written as
`isinstance(tree, exp.Select) → ok` accepts both and is theater. Only walking the
whole tree catches them — see `FORBIDDEN_NODES` in
[guardrails/validator.py](guardrails/validator.py).

`exp.Command` is in that set too. It is sqlglot's fallback for any statement it
does not model — `VACUUM`, `REINDEX`, `CALL`, `COPY ... TO PROGRAM` — so
rejecting it closes a whole class in one line. It is the check people forget.

### Why parse to a list, never `parse_one`

`sqlglot.parse()` returns a list. `SELECT 1; DROP TABLE users` is two
expressions; `parse_one()` silently returns the first and drops the rest on the
floor. Anything other than exactly one statement is rejected.

### Why the row cap and the timeout are both needed

They bound different resources and neither substitutes for the other.

`LIMIT` bounds rows *returned* — the response payload and the memory the API
holds. It does **not** bound work *done*: `SELECT … FROM billion_row_table GROUP
BY x LIMIT 10` still computes the entire aggregate before discarding all but ten
rows.

`statement_timeout` bounds server CPU. It must be set at the connection
(`SET LOCAL statement_timeout` inside the transaction, in
[api/database.py](api/database.py)) rather than wrapped around the call in
Python — an application-level timeout cancels *our waiting* while Postgres
happily keeps burning a core on the query.

### Why the guardrail is three layers, not one

If the AST validator were the only enforcement, one parser bug would be total
compromise. So:

1. **Role grants.** The app authenticates as `analyst_ro`, which holds `SELECT`
   and nothing else. It physically cannot write, whatever SQL reaches it.
2. **Read-only transactions.** `default_transaction_read_only = on` on that role,
   plus `SET LOCAL transaction_read_only` per query. Postgres aborts writes at
   the transaction level.
3. **The AST validator.** Catches what layers 1 and 2 do not: resource
   exhaustion, the row cap, filesystem and eval functions — and, importantly, it
   produces a *structured rejection reason* the repair node can hand back to the
   model. `permission denied for table customers` is a much worse repair signal
   than `DELETE is not allowed`.

Layers 1 and 2 are in [sql/schema.sql](sql/schema.sql) and
[api/database.py](api/database.py).

### Why the validator never raises

Every failure returns `ok=False` with a reason. An exception escaping the
`validate` node would crash the graph rather than route to `repair`, so a
malformed generation would become a 500 instead of a retry. "Fails closed" and
"never raises" are the same requirement seen from two sides.

## State design

Full annotations in [agent/state.py](agent/state.py). The four decisions worth
defending:

**`db_error` is its own key, not a field inside `execution_result`.** Partly
provability — `repair` reads `state["db_error"]`, written in exactly one place,
so "the DB error is fed back" is a one-grep claim. Mostly because a validation
failure and an execution failure need different repair prompts, and the repair
node branches on which key is populated rather than sniffing strings.

**`generated_sql` and `safe_sql` are separate.** `generated_sql` is the verbatim
model output, kept so the trace is honest about what the model actually wrote.
`safe_sql` is the post-guardrail text, and it is the only thing `execute` will
run — if execute fell back to `generated_sql`, the injected `LIMIT` would be
silently discarded and the row cap would be decorative. `execute` raises rather
than falling back.

**`retry_count` lives in state.** Nodes must be pure `state -> partial state` so
the graph can be checkpointed, interrupted and resumed. A module-level counter
would also be shared across concurrent FastAPI requests. It is incremented in
`repair` and nowhere else.

**`attempts` uses an append reducer** (`Annotated[list, operator.add]`).
Everything else is last-write-wins, which is correct for a current-value field
and wrong for a trace — the frontend needs plan → attempt 1 → error → attempt 2
→ final, and an overwriting field would only ever show the last one.

### Why `repair` does not write SQL

`repair` makes no model call. It classifies the failure, increments the counter,
writes a `repair_instruction`, and routes back to `generate`. The alternative —
`repair` generating corrected SQL itself — means two prompts that both emit SQL
and drift apart, and two edges that must both route through `validate`. One
careless `repair → execute` edge and the guardrail is bypassed while the graph
still looks correct. Keeping `generate` as the single SQL-producing node means
there is exactly one path to the database.

The one thing `repair` does decide is *where* to go back to. A missing
relation or column means the **plan** is wrong, and regenerating SQL from the
same plan would produce the same bad table name until the retries run out — so
those route to `plan`. Everything else routes to `generate`, which is the cheap
path.

## What keeps the claims honest

[tests/test_repair_loop.py](tests/test_repair_loop.py) runs the real graph
against a fake model and a fake database. Each test targets a failure that would
otherwise be invisible — the graph still cycles, the trace still shows attempts,
the API still returns 200:

- `test_db_error_is_fed_back_into_generate` — asserts the driver error text and
  the previous SQL appear in the *second* prompt, and that repair text is absent
  from the first. Without this, "repair" could be a blind retry.
- `test_validation_rejection_is_fed_back_into_generate` — same for guardrail
  rejections, asserted against whatever reason the validator actually produces
  rather than a hardcoded string.
- `test_execute_only_ever_runs_validated_sql` — the statement the fake DB
  received is the one with the injected `LIMIT`.
- `test_guardrail_blocks_reach_the_database` — stacked statements and
  `SELECT … INTO` never appear in the executed list.
- `test_loop_gives_up_and_reports_failure` — bounded retries, explicit
  `status="failed"`.

`87 passed` across the guardrail suite and the graph suite.

## Known trade-offs

- **The schema is loaded once at startup** and closed over by the nodes rather
  than carried in graph state, because state is serialized at every checkpoint
  and the DDL never changes during a run. If the schema outgrows the prompt,
  [agent/introspect.py](agent/introspect.py) is the seam where retrieval goes —
  and at that point the selected subset *does* belong in state, because it
  varies per question.
- **No server-side refusal fallbacks.** The Anthropic docs recommend passing
  `fallbacks` on Opus-5-class models, but that parameter lives on
  `client.beta.messages` while the typed `messages.parse` helper lives on the
  stable client. Text-to-SQL over your own schema is a low-refusal workload, so
  this build keeps the typed parse and handles `stop_reason == "refusal"`
  explicitly instead. See [agent/llm.py](agent/llm.py).
- **No checkpointer.** The graph compiles without one, so runs are in-memory and
  a crashed request is lost. Adding `MemorySaver` or a Postgres checkpointer is
  a one-line change; `retry_count` already lives in state precisely so that
  works.
